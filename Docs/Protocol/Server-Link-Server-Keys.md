# Server Keys for the Server Linking Extension

> **Status:** Proposal by Misha Nasledov ([@mishan](https://github.com/mishan)), **adopted** into the [Server Linking Extension](Capabilities-Server-Link.md) in its fifth revision, October 2026. Server keys, key mode and the key proof are now defined there, in [Server Key](Capabilities-Server-Link.md#server-key), [Server Keys over TLS](Capabilities-Server-Link.md#server-keys-over-tls) and [The Key Proof](Capabilities-Server-Link.md#the-key-proof), and that text governs. Its field IDs, `0x0640`-`0x0641`, are assigned there as `DATA_LINK_SERVER_KEY` and `DATA_LINK_KEY_PROOF`.
>
> This document is kept as the original proposal, and for its [Possible Follow-ups](#possible-follow-ups), which are **not** adopted. On adoption, the extension changed the following around key mode itself:
>
> - every server SHOULD have a key and use the ID derived from it, whether or not it uses key mode, so the ID changes once and key mode is a per-link choice;
> - a server that changes its ID closes its links with `Shutdown`, never `Unlinked`, and peers withdraw the old server when its Hello names a new one;
> - key logins SHOULD NOT count toward account lockout;
> - reusing the key elsewhere is allowed for any use whose signatures are domain-separated from the key proof's.

An optional addition to the [Server Linking Extension](Capabilities-Server-Link.md), written in that document's format and linking to its sections.

This is deliberately a small first step: links authenticated by server keys instead of a shared password. Signing what crosses relays, and signing moderation, would build on it, and I've sketched both under [Possible Follow-ups](#possible-follow-ups) together with why I left them out.

---

## Server Keys

A server MAY hold an Ed25519 **server key** and use it to authenticate its links instead of a password. Operators exchange public keys instead of shared secrets:

- **Mutual authentication without a shared secret.** Each side proves its key during login, so there is no password to guess offline, nothing secret passes between operators, and nothing needs rotating when an operator leaves.
- **A server ID no peer can be mistaken about.** A keyed server's ID is derived from its key, so a peer linked in key mode knows the ID at the other end is genuine.

Server keys are optional, per server and per link. A network can mix keyed and unkeyed servers, and links that use passwords work exactly as today.

### The Server Key

- An Ed25519 key pair (RFC 8032), generated by the server and kept permanently, like the [server ID](Capabilities-Server-Link.md#server-id). Implementations SHOULD keep it apart from the configuration an operator copies between servers, for the reasons given under Server ID.
- Shown to operators as its **fingerprint**: the SHA-256 digest of the 32-byte public key, displayed as lowercase Crockford base32 (most significant bit first, as RFC 4648) without padding (52 characters). Operators compare fingerprints when they exchange keys, as they would an SSH host key.
- A server MUST refuse a public key, whether configured for a peer or its own, that is not a canonical encoding or is a point of small order.
- A server that also serves Hotline-ng discovery MAY use the same key it publishes there as `server_key` (base64url), so a peer's operator can compute its fingerprint from the peer's discovery document instead of taking it on trust. The `hotline-link-` signature domain below does not overlap Hotline-ng's.

### Server ID from the Key

A keyed server's server ID is **the first 8 bytes of the raw SHA-256 digest of its public key** (not of the base32 display form). It MUST NOT use any other ID while it has the key.

**Adopting, changing or dropping a key changes the server ID**: to the one derived from the new key, or, for a server that stops using keys, to a new random ID. On a keyed server, the command that generates a new server ID (`janus link reset-id` in the reference server) therefore generates a new key. The server MUST close every link with `Unlinked` before using its new ID, so peers discard the old server at once rather than hold it for the grace period. Its own dialers then retry at the slowest pace until each peer's operator has configured the change. Bans it made under its old ID stay with that ID, and it can no longer unban them.

### Protecting the Link: Server Keys over TLS

A third row for the table in [Protecting the Link](Capabilities-Server-Link.md#protecting-the-link):

| Protection | Requirements |
|---|---|
| **Server keys over TLS** | TLS 1.3, negotiated and terminated by the server process itself. The certificate need not be verified: each side proves its server key during login, bound to the TLS session ([The Key Proof](#the-key-proof)), and each side MUST verify the other's proof against the key its operator configured for that peer |

The proof is what makes an unverified certificate acceptable here. It is bound to this TLS session's exporter value, which depends on the whole handshake, so a man in the middle holding two TLS sessions cannot carry a proof from one into the other.

- Both sides MUST refuse key mode unless TLS 1.3 was negotiated. Login (107) MUST NOT be sent as 0-RTT early data, and the early exporter MUST NOT be used.
- Key mode cannot work behind a proxy that terminates TLS on the server's behalf (stunnel, a reverse proxy in front of a WebSocket carrying the classic protocol), because the server has no exporter for a session it did not terminate. A link through such a proxy uses a password.
- A link uses either a password (HOPE AEAD or verified TLS, as today) or server keys, as its operators configure. A dialing entry in key mode carries the peer's address, the account name the peer issued, and the peer's public key. An accepting entry names the local account the peer logs in with and the peer's public key.
- **A key-mode link account can never log in with a password.** It is stored with a password that matches nothing (not an empty one), so that it stays closed to ordinary logins even if its accepting entry is later removed and the account left behind.
- If an operator changes the key configured for a peer while its link is up, the server closes the link with `ProtocolError`, and the link returns by itself once both sides agree (see the retry rule under [The Key Proof](#the-key-proof)). Until then, the side still holding the old key reports a possible impersonation; operators rotating a key should expect that.

### The Key Proof

Each side computes the TLS 1.3 exporter value for the session (RFC 8446 section 7.5) with label `EXPERIMENTAL-hotline-link-key-proof`, an empty context and a length of 32 bytes, and signs:

```
"hotline-link-key-proof-v1" || 0x00 || role || exporter || signer_key || peer_key
```

| Item | Size | Value |
|---|---|---|
| `role` | 1 | `0x01` when the dialer signs, `0x02` when the acceptor signs |
| `exporter` | 32 | The exporter value |
| `signer_key` | 32 | The signer's public key |
| `peer_key` | 32 | The public key the signer expects at the other end |

`role` keeps either side from reflecting the other's proof back. `peer_key` binds the proof to the server the signer meant to reach. A verifier rebuilds the bytes from the other side's role, its own exporter value, the key configured for the peer as `signer_key` and its own key as `peer_key`. It never takes them from the wire, and it verifies with that configured key, already checked as described under [The Server Key](#the-server-key).

**Login (107)** from a key-mode dialer carries, alongside `DATA_CAPABILITIES` with bit 11 set, `DATA_LINK_SERVER_KEY` (the dialer's public key) and `DATA_LINK_KEY_PROOF` (the dialer's proof). The password field is empty.

The acceptor confirms bit 11 only when all of the following hold:

1. the account is the link account of an accepting entry in key mode;
2. that entry's configured key equals `DATA_LINK_SERVER_KEY`;
3. the proof verifies.

Otherwise, including when a valid proof arrives on a login that does not set bit 11, it refuses the login like any failed login, and does not check the password field. A successful login reply carries the acceptor's `DATA_LINK_SERVER_KEY` and its own proof.

The dialer MUST verify that the acceptor's key equals the key configured for that peer and that its proof verifies. If either check fails, or the reply lacks either field, it MUST disconnect without sending any further transaction and SHOULD report it to its operator as a possible impersonation, not a configuration error.

**Retrying.** A failed key check on either side, whether the acceptor refuses the dialer's login or the dialer refuses the acceptor's proof, is not final. The dialer keeps retrying at its slowest pace, as for `Suspended`, and keeps reporting each failure to its operator, overriding the base spec's advice ([Capability Bit](Capabilities-Server-Link.md#capability-bit)) not to retry a login that did not confirm bit 11. A key rotation staged on both sides then completes on its own.

**Hello.** On a key-mode link, the server ID in a received Link Hello MUST be the one derived from the key its sender proved at login. A Hello with any other server ID closes the link with `ProtocolError`.

Because the certificate is not verified, the dialer reveals its key, its account name and the fact that it links to whoever answers its connection before that party has proven anything. An impostor learns no secret, but it does learn of the link. Operators to whom that matters can use a certificate their peer verifies, in addition to the key proof.

| ID (hex) | Dec | Name | Type | Description |
|---|---|---|---|---|
| `0x0640` | 1600 | `DATA_LINK_SERVER_KEY` | Binary (32) | An Ed25519 server public key, in Login (107) and its reply |
| `0x0641` | 1601 | `DATA_LINK_KEY_PROOF` | Binary (64) | A [key proof](#the-key-proof) signature, in Login (107) and its reply |

### Security Considerations

- **The private key is the keys to the user list**, as the link password is now. The difference is that it never leaves the server that holds it. A peer's operator holds only a public key, which is useless to anyone who steals it.
- **Revocation is unilateral.** An operator who no longer trusts a key removes the peer's entry. A server whose key leaked generates a new one, and with it a new server ID, and gives the new fingerprint to its peers.
- **What a key proves.** Key mode authenticates the two servers on a link to each other. It says nothing about servers further away: what a peer relays about them is taken on trust, exactly as on a password link.

### Implementation Notes

- Exporter values are available as `tls.ConnectionState.ExportKeyingMaterial` in Go and `export_keying_material` in rustls, among others. Both expose whether TLS 1.3 was negotiated.
- Neither Go's `crypto/ed25519` nor `ed25519-dalek` refuses every non-canonical or small-order public key on its own. Since a verifier only ever uses configured keys, the check belongs where a key is configured or generated: decode to a point, re-encode the point and compare bytes for canonical form, and multiply by the cofactor and compare with the identity for small order. In Go, `filippo.io/edwards25519` does both (`SetBytes` then `Bytes`; `MultByCofactor`). In Rust, `ed25519-dalek`'s `VerifyingKey::is_weak` covers small order, but its `to_bytes` returns the bytes it was given, so the canonical check must re-encode through the point, as in `CompressedEdwardsY(bytes).decompress()?.compress() == bytes`.
- hxd-ng would use the same Ed25519 key here as its `server_key` in Hotline-ng discovery.

## Possible Follow-ups

Both of these build on server keys, and [Relaying Fields](Capabilities-Server-Link.md#relaying-fields) carries their fields across servers that don't implement them. I drafted each, and found enough hard edges that I'd rather they get their own design than hold this up.

**Signed server groups across relays.** A keyed server would sign its own server group, so that a server in the middle could relay it but not invent it, alter it or bring back an old copy, and receivers would pin the keys they have seen. The hard parts:

- the signer needs a counter that only ever increases, survives crashes and restores, and can't be wedged by one clock jump;
- receivers need a pin table whose learned entries expire only while the server is absent, so the guard can't be erased or exhausted;
- a group that fails a check must not hide a server that is already shown, nor partition everything behind a relay with a bad clock.

Even done well, it proves a group's content and not where the server sits.

**Signed moderation.** Kicks, bans and unbans signed by the requesting server and checked by a keyed home server, with signed replies. It would buy:

- attribution of every request to the server that made it;
- unbans that only the banning server can make;
- no redirecting a moderator's request to someone else;
- results a middle server can't fake.

It would not stop a middle server from banning anyone in the name of a server the home server has never seen. It needs the home server's own user ID and epoch carried in user groups (with the spec's [ID quarantine](Capabilities-Server-Link.md#user-ids-on-a-link), those name one session for longer than a signed request lives), the requester's key in each request, a short history of each session's names, synced clocks and two new reason codes. That is a lot of machinery for what it buys, so it may be worth weighing against simpler alternatives first.
